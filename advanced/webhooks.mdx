## Overview

Webhooks notify your application when events happen in Recurso:

- Subscription changes
- Payment events
- Invoice updates
- Customer actions

## Register a Webhook

```typescript
const webhook = await recurso.webhooks.create({
  url: 'https://yourapp.com/webhooks/recurso',
  events: [
    'subscription.created',
    'payment.succeeded',
    'payment.failed',
    'invoice.paid'
  ],
  secret: 'your-webhook-secret'  // Auto-generated if not provided
});
```

## Verify Signature

Always verify webhook signatures:

<CodeGroup>
```typescript TypeScript
import crypto from 'node:crypto';
import express from 'express';

app.post('/webhooks/recurso', 
  express.raw({ type: 'application/json' }),
  (req, res) => {
    // Verify manually — the SDKs ship no constructEvent helper.
    // Recompute HMAC-SHA256 (hex) over the RAW body with your
    // endpoint's signing secret and compare in constant time.
    const signature = req.headers['x-recurso-signature'];
    const expected = crypto
      .createHmac('sha256', process.env.WEBHOOK_SECRET)
      .update(req.body) // raw Buffer — never JSON.stringify
      .digest('hex');
    const valid =
      typeof signature === 'string' &&
      signature.length === expected.length &&
      crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected));

    if (!valid) {
      console.error('Webhook signature verification failed');
      return res.sendStatus(400);
    }

    const event = JSON.parse(req.body);
    switch (event.type) {
      case 'subscription.created':
        handleSubscriptionActivated(event.data);
        break;
      case 'payment.failed':
        handlePaymentFailed(event.data);
        break;
    }

    res.sendStatus(200);
  }
);
```

```python Python
import hashlib, hmac, json, os
from flask import Flask, request

@app.route('/webhooks/recurso', methods=['POST'])
def webhook():
    # Verify manually — the SDKs ship no construct_event helper.
    signature = request.headers.get('X-Recurso-Signature', '')
    expected = hmac.new(
        os.environ['WEBHOOK_SECRET'].encode(),
        request.get_data(),  # raw body, before any JSON parsing
        hashlib.sha256,
    ).hexdigest()

    if not hmac.compare_digest(signature, expected):
        return 'Invalid signature', 400

    event = json.loads(request.get_data())
    if event['type'] == 'subscription.created':
        handle_activation(event['data'])

    return '', 200
```
</CodeGroup>

## Event Types

Recurso emits exactly these ten event types:

### Subscription Events

| Event | Description |
|-------|-------------|
| `subscription.created` | New subscription started |
| `subscription.renewed` | Billing period advanced after successful renewal |
| `subscription.canceled` | Subscription canceled |

### Payment Events

| Event | Description |
|-------|-------------|
| `payment.succeeded` | Payment completed |
| `payment.failed` | Payment attempt failed |

### Invoice Events

| Event | Description |
|-------|-------------|
| `invoice.created` | New invoice generated |
| `invoice.paid` | Invoice paid in full |
| `invoice.payment_failed` | Payment attempt on the invoice failed |

### Customer Events

| Event | Description |
|-------|-------------|
| `customer.created` | New customer |
| `customer.updated` | Customer updated |

Pauses, refunds, and disputes are visible on their resources (and in the
[Events feed](/advanced/developer-settings)) but do not have dedicated
webhook types today — subscribe to the list above only.

## Retry Policy

Failed deliveries are retried with exponential backoff: `2^attempt × 30s`, capped at 24 hours between attempts. Any non-2xx response (or a transport error) counts as a failure.

After **5 attempts** the delivery becomes terminal: it is marked `failed` with the last HTTP status code and error body recorded, and the worker stops retrying it. Terminal deliveries are never picked up again automatically — use [redelivery](#delivery-tracking--redelivery) to start a fresh cycle.

## Delivery Tracking & Redelivery

Every delivery attempt is recorded per event × endpoint. Each record carries a derived status:

| Status | Meaning |
|--------|---------|
| `pending` | Queued for the first attempt, or waiting for the next retry (`next_retry_at` set) |
| `succeeded` | The endpoint acknowledged with a 2xx response (`delivered_at` set) |
| `failed` | 5 attempts exhausted, or the request could not be built; `last_error` has the reason |

### Inspect deliveries

Per endpoint (the delivery log for one receiver, with status filter and pagination):

```typescript
const failing = await recurso.webhooks.deliveries('wh_xyz', {
  status: 'failed',
  limit: 20,
});
```

Per event (did every endpoint receive event X?):

```typescript
const deliveries = await recurso.events.deliveries('evt_abc');

// Returns
{
  data: [
    {
      id: 'del_123',
      event_id: 'evt_abc',
      webhook_endpoint_id: 'wh_xyz',
      endpoint_url: 'https://yourapp.com/webhooks/recurso',
      status: 'failed',
      attempts: 5,
      last_status_code: 500,
      last_error: 'HTTP 500: internal server error',
      created_at: '2026-07-06T10:30:00Z'
    }
  ]
}
```

### Redeliver an event

Redelivery resets the event's delivery records to `pending` — attempt counter cleared, fresh retry cycle — for every active endpoint subscribed to the event's type, and returns `202` immediately (the worker delivers on its next poll):

```typescript
const result = await recurso.events.redeliver('evt_abc');
// { data: { event_id: 'evt_abc', deliveries_queued: 2 } }
```

Redelivery is idempotent: repeated calls reset the same records rather than creating duplicates. Inactive endpoints are skipped (`deliveries_queued: 0` when nothing subscribes). Because your receiver may see the same event ID more than once, keep webhook handlers idempotent.
