## Base URL

```
https://api.recurso.dev/v1
```

<Note>
`api.recurso.dev` is a placeholder — substitute the domain where your Recurso instance is deployed. All API examples in this reference use the same placeholder.
</Note>

## OpenAPI Specification

Every Recurso instance serves its own OpenAPI 3.1 spec at `/openapi.json`
(and `/openapi.yaml`) — no authentication required. The interactive
playground in this reference is powered by a vendored copy of the same
spec, so you can also point code generators or API clients directly at
your running instance:

```bash
curl https://api.recurso.dev/openapi.json
```

## Postman collection

A ready-to-import Postman collection covering every endpoint (generated from the
OpenAPI spec, grouped by resource) lives in the repository under
[`postman/`](https://github.com/recurso-dev/recurso/tree/main/postman).

Import both `recurso.postman_collection.json` and
`recurso.postman_environment.json`, select the **Recurso** environment, then set
`baseUrl` (your instance) and `bearerToken` (an API key from **Developers**).
Every request then authenticates automatically — see
[`postman/README.md`](https://github.com/recurso-dev/recurso/blob/main/postman/README.md)
for the regenerate command.

## Authentication

Authenticate using API keys in the `Authorization` header:

```bash
curl https://api.recurso.dev/v1/customers \
  -H "Authorization: Bearer rsk_live_xxx"
```

<Warning>
Keep your API keys secret. Never expose them in client-side code.
</Warning>

### API Key Types

| Type | Prefix | Use Case |
|------|--------|----------|
| Live | `rsk_live_` | Production |
| Test | `rsk_test_` | Development/testing |

Test keys only work with test data and test payment methods.

## Request Format

All requests use JSON:

```bash
curl -X POST https://api.recurso.dev/v1/customers \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme Corp",
    "email": "billing@acme.com"
  }'
```

## Response Format

Every success response wraps the result in a top-level `data` field. Object ids
are **UUIDs** — there is no `object` type field or resource-prefixed id.

```json
{
  "data": {
    "id": "b9071c55-0e14-4720-80f3-665613ceb7de",
    "name": "Acme Corp",
    "email": "billing@acme.com",
    "created_at": "2024-01-15T10:30:00Z"
  }
}
```

### List Responses

Collections return an array under the same `data` field:

```json
{
  "data": [
    { "id": "b9071c55-0e14-4720-80f3-665613ceb7de", "name": "Acme Corp" },
    { "id": "06c151de-8d3a-4b21-9c77-2f0e5a9b4d12", "name": "Globex" }
  ]
}
```

<Note>
  A few endpoints deviate from the `{data}` wrapper (auth and import handlers
  return bare objects; action endpoints return `{status}` / `{message}`). Each
  endpoint's reference page shows its exact shape.
</Note>

## Pagination

Use `limit` and `offset` for pagination:

```bash
GET /v1/customers?limit=20&offset=40
```

| Parameter | Default | Max |
|-----------|---------|-----|
| `limit` | 50 | Varies by endpoint (up to 1000) |
| `offset` | 0 | — |

<Note>
  List endpoints don't return a total count or `has_more` flag — page until you
  receive fewer rows than your `limit`. Always pass an explicit `limit` when you
  need a full set, since defaults differ across endpoints.
</Note>

## Errors

Every error — regardless of endpoint or status code — uses the same
envelope: an `error` object with a stable machine-readable `code` and a
human-readable `message`:

```json
{
  "error": {
    "code": "not_found",
    "message": "Customer cust_xyz not found"
  }
}
```

See [Errors](/api-reference/errors) for the full code taxonomy.

### HTTP Status Codes

| Code | Meaning |
|------|---------|
| `200` | Success |
| `201` | Created |
| `400` | Bad Request |
| `401` | Unauthorized |
| `404` | Not Found |
| `422` | Validation Error |
| `429` | Rate Limited |
| `500` | Server Error |

## Rate Limits

Rate limits depend on your [Recurso plan](/pricing):

| Plan | Requests/min | Description |
|------|--------------|-------------|
| [Open Source](/pricing) | Unlimited (self-configured) | Self-hosted, configure your own limits |
| [Cloud](/pricing) | 600 | Managed hosting, free to start |
| [Enterprise](/pricing) | Custom | Dedicated infrastructure with custom limits |

<Tip>
Self-hosted users can configure their own rate limits with no restrictions. See the [Developer Settings guide](/advanced/developer-settings) for configuration options.
</Tip>

Rate limit info in response headers:

```
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 599
X-RateLimit-Reset: 1705312800
```

## Idempotency

On any mutating request (POST, PUT, PATCH, DELETE), send an `Idempotency-Key`
header to prevent duplicate operations — a replayed key returns the original
stored response (marked with `X-Idempotency-Hit: true`):

```bash
curl -X POST https://api.recurso.dev/v1/subscriptions \
  -H "Authorization: Bearer $API_KEY" \
  -H "Idempotency-Key: unique-request-id-123" \
  -d '{ ... }'
```

<Tip>
Use UUIDs or your own unique identifiers as idempotency keys.
</Tip>

## Versioning

API version in header (optional):

```
Recurso-Version: 2024-01-01
```

Without version, you get the latest stable API.
